# ZEB-ROI 아키텍처 · 큰 틀

> **최종 방향**: AI Agent 기반 ZEB / 그린리모델링 평가 및 ROI 산정
> 최종 갱신: 2026-07 · 상태: 방향 확정, 단계적 구현 중

---

## 0. 한 줄 정의

> **BIM 한 번 입력으로 ZEB 인증 등급과 그린리모델링 사업 경제성을 동시에 산출하는 AI Agent 플랫폼.**
> 계산·판정은 결정론적 엔진과 물리 시뮬레이션이, 언어와 오케스트레이션만 LLM이 담당한다.

---

## 1. 설계 원칙 (타협 금지)

| # | 원칙 | 이유 |
|---|------|------|
| **P1** | **파인튜닝 대신 Agent + RAG** | 단가·법령·보조율이 수시로 바뀐다. 파인튜닝은 학습 시점에 지식이 고정돼 stale해지고, 재학습 비용이 크며, 갱신 이력을 추적할 수 없다. |
| **P2** | **계산은 절대 LLM에게 시키지 않는다** | LLM의 역할은 ① 자연어 → 파라미터 추출 ② 도구 호출(오케스트레이션) ③ 결과 → 자연어 설명. **숫자는 전부 엔진이 만든다.** |
| **P3** | **법령은 RAG로 원문 인용, 없으면 없다고 답한다** | 법령 환각은 실무에 치명적. 검색된 조항 밖의 내용은 생성하지 않고 출처(파일·페이지)를 함께 제시한다. (실무 담당자 피드백으로 검증) |
| **P4** | **ZEB와 그린리모델링은 판정 로직을 분리하되, 데이터·해석 기반은 공유한다** | 법적으로 다른 제도라 판정은 분리해야 한다. 그러나 같은 건물을 두 번 파싱하면 숫자가 어긋난다. **공유 코어 위에 두 트랙**을 얹는다. |

## 3. 두 트랙 분리 (P4)

같은 건물, 다른 제도. **판정은 분리, 기반은 공유.**

| | **Track A · ZEB 인증** | **Track B · 그린리모델링 사업** |
|---|---|---|
| 목표 | 인증 등급 취득 | 사업 선정 + 경제성 확보 |
| 근거 | ZEB 인증기준 고시 (제1·2·3호) | GR 가이드라인 종합형 정량평가표 |
| 판정 | 자립률 **또는** 1차에너지소요량, **그리고** BEMS → +등급~5등급 | 100점 (기술요소 80 + 사업여건 20) → A+~D |
| 핵심 수치 | 에너지자립률, 1차에너지소요량(×2.75) | 보강 우선순위, Max Cost, 보조금, 자부담 |
| 담당 | ZEB 팀 | 그린리모델링 팀 |
| **공유 코어** | **BIM 파싱 · 에너지 해석 · 단가DB · 법령 RAG — 하나만 존재** | |

> ⚠️ **팀을 2개로 나누되, 공유 코어의 인터페이스(공통 건물모델 스키마 + 해석 결과 스키마)를 먼저 합의하고 나눌 것.**
> 인터페이스 합의 없이 병렬로 가면 같은 건물에서 두 팀의 숫자가 어긋난다.

## 5. 에너지 해석 업그레이드 (가장 중요한 과제)

### 현재 (간이 추정)
```python
# core/zeb_evaluator.py
BASE_ENERGY_BY_USE = {"어린이집": 200, ...}   # 용도별 원단위 kWh/㎡·년
GR_ENERGY_REDUCTION = {"3_외벽단열보강": 0.15, ...}  # 요소별 절감률(가정치)
```
- 장점: 빠르고 의존성 없음, 무료 티어에서 동작
- 한계: **"왜 15%인가?"에 답할 근거가 약함.** 건물 형상·기후·향·창면적비가 반영되지 않음

### 목표 (물리 기반 시뮬레이션)
```
Revit → gbXML → OpenStudio(SDK) → IDF → eppy(파라미터 조작) → EnergyPlus 실행
     → 연간 소요량·절감량(kWh) → ZEB 자립률/등급 → ROI
```
- **eppy는 IDF 편집·실행 래퍼이지 지오메트리 생성기가 아니다.** 형상은 gbXML/OpenStudio가 만든다.
- EnergyPlus 실행 파일이 필요 → **Streamlit 무료 티어(1GB)에서 실행 불가.**
  → **해석은 로컬/배치로 돌리고 결과를 캐시**하는 구조로 간다. (웹은 결과 조회·시나리오 비교만)
- 검증 지표로 **CVRMSE ≤ 15%** (실측 대비) 도입 검토 — UBEM 표준 관행

### 얻는 것
ROI가 **가정치 절감률**이 아니라 **시뮬레이션 절감량(kWh)** 을 먹게 되면 체인 전체의 신뢰도가 완성된다:
> BIM 형상 → 물리 시뮬 → 절감량 → ZEB 등급 → 경제성

## 6. BIM 입력 경로 — 공부항목 ①에 대한 결론

> **질문: "revit 파일을 웹서버에 넣고 분석이 되는지? rvt으로 해석하면 메리트가 클 것 같음"**

**결론: `.rvt`를 웹서버에서 직접 파싱하는 것은 사실상 불가능하다.** `.rvt`는 Autodesk 독점 바이너리 포맷이고 공개 파서가 없다. 서버에서 열려면 Revit이 설치된 Windows가 필요하다.

현실적인 3가지 경로:

| 경로 | 방법 | 장점 | 단점 | 추천 용도 |
|---|---|---|---|---|
| **A. APS(구 Forge)** | `.rvt` 업로드 → Model Derivative API로 IFC/속성 변환 | **.rvt 그대로 업로드 가능** | 클라우드 의존·계정 필요, 변환 대기 | "rvt 그대로"가 꼭 필요할 때 |
| **B. IFC** | Revit에서 IFC export → `ifcopenshell`(Python) | 개방 표준, 무료, 벤더 종속 없음, 물량 추출 강함 | export 1회 수동 | **물량·객체 분석** |
| **C. gbXML** ⭐ | Revit에서 gbXML export → OpenStudio/EnergyPlus | **애초에 에너지 해석용 포맷**, Revit 기본 지원 | 형상 단순화 이슈 | **에너지 해석** |
| D. Dynamo JSON | 현재 방식 | 이미 동작 | Revit+Dynamo 수동 단계 | fallback 유지 |

**권장**: **에너지 해석 = gbXML**, **물량·객체 = IFC**, **JSON은 fallback으로 유지.**
"rvt를 웹에 올려서 바로"는 APS를 붙이면 가능하지만, 졸업설계 스코프에서는 gbXML/IFC가 훨씬 저렴하고 확실하다.
(디자인빌더에서 파일이 깨진 문제도 gbXML 경로로 우회 가능성이 높다 — 형상을 다시 그리지 않고 export 설정만 조정)
